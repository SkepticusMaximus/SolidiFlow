Who this is for

This primer touches four overlapping audiences and tries to flag which one a section is speaking to:

  1. The SolidiFlow user. Someone designing a contract by drawing it in the SolidiFlow GUI. Doesn't write Solidity by hand.
  2. The plugin developer. Someone implementing the SolidiFlow GUI and code generator (React / TypeScript inside a Remix plugin). Reads Solidity reference material to be sure the generator emits valid output.
  3. The contract author for CGP / P2PCP. A specific SolidiFlow user designing the protocol's actual contracts. Same as audience 1 but with concrete contract requirements in mind.
  4. The Solidity reader. Anyone who needs to verify what SolidiFlow's generator produced, or argue about whether it's correct.

The substrate underneath all four is an understanding of Ethereum's architecture and ecosystem. Most of the early sections build that substrate.

1. Glossary — the terms before the terms

Several terms in this primer have everyday meanings that don't match the meanings used in this domain. Read these once before going further; come back when needed.

Contract A small program permanently deployed to a blockchain. Has its own address, its own persistent storage, and its own callable functions. A legal document.
State The data a contract has stored in its persistent on-chain storage. Survives between calls. A condition or status indicator (although such things are often kept in state).
Solidity The high-level programming language that smart contracts on Ethereum are typically written in. Compiles to EVM bytecode. Anything other than the language itself.
EVM Ethereum Virtual Machine. The runtime that executes deployed contracts. Every Ethereum node runs an EVM. A virtual machine you install on your laptop.

Gas The unit of computational cost on Ethereum. Every operation costs gas; the user sending the transaction pays. A fluid, fuel, or vapour.

2. Three categories: mandated, chosen, generated

Throughout this primer, every piece of code text falls into one of three categories. Recognising which category a piece belongs to is the single most useful skill for reading Solidity (or any other language) without getting lost.

CategoryWhat it isExample
mandated Reserved keywords and required syntax built into the Solidity language. You cannot pick something else; the compiler will reject the file if you try. function, public, require, uint256, address, mapping, semicolons, braces.
chosen Identifiers that the developer picks freely, within naming rules. Variable names, function names, contract names, parameter names, event names, modifier names. They become part of the contract's public API but are arbitrary. oracle, balances, mint, onlyOracle, computeUnits.

4. A mental model for Ethereum and smart contracts

Audience for this section

Foundational. Required reading for all four audiences. The decisions a contract author makes — and the code SolidiFlow generates — only make sense in light of what kind of machine the EVM is.

A smart contract is a small program permanently deployed to a blockchain. Once deployed, its code cannot be changed (without specific upgrade patterns). Anyone can call its public functions by sending a transaction. Each call costs gas, paid by whoever sent the transaction. The result of a call is computed deterministically — given the same starting state and the same arguments, every Ethereum node in the world independently re-executes the call and must arrive at the same answer. This is the only way the network as a whole can agree on what happened.

This determinism requirement is not a stylistic choice. It's the precondition for the network's existence. If two honest nodes ran the same call against the same starting state and got different answers, they would disagree about what the chain looks like, and the network would fork.

What the EVM forbids, and why

Three things would naturally produce different answers on different machines, so the EVM forbids them:

Random numbers. A truly random function would return a different value on every node. So Solidity has no built-in random(). You can derive deterministic pseudo-random values from on-chain data like block.prevrandao, but they are predictable and weak as randomness sources. For anything financially serious, contracts use an oracle service like Chainlink VRF, which delivers a verifiable random number on-chain where every node sees the same value.

Network calls. A contract calling api.example.com would see different responses (or timeouts) on different nodes. So contracts have no network primitives at all — no fetch, no sockets, no DNS. To bring outside-world data on-chain, an oracle service writes the data into a special on-chain contract, and your contract reads it from there.

Real-world time. Every node mines or validates blocks at slightly different real-world moments. There's no global "now". What Solidity exposes instead is block.timestamp — the timestamp the validator stuck in the current block's header. All nodes see the same value for a given block (because they're reading the same header), so it is deterministic. But it's coarse (Ethereum blocks are about 12 seconds apart) and the validator can fudge it within a small window. Fine for "after deadline X" coarse logic; useless for finer timing.

The flip-side: a contract can read anything that has already been agreed onto the chain. Its own state, other contracts' state (via interface calls), the current block's number and timestamp, the address of whoever called it — all fine. Anything that requires asking the outside world live, on-the-fly, breaks consensus.

State, transactions, gas

A contract has state — a small, expensive, persistent database stored on-chain — and functions that read or modify it. There is no main loop. The contract simply waits to be called. When called, a function runs to completion, every state change it made is committed to the chain, and the contract goes back to sleep until the next call.

If the function reverts (for any reason), all of its state changes are rolled back as if the call never happened. The user still pays gas for the work the EVM did up to the revert, but the chain's state is unchanged. This atomicity is per-transaction, not per-statement. A function partway through writing ten state variables and then hitting a failed require simply leaves all ten as they were before the call.

Most of the safety patterns in Solidity are some flavour of require:

require(/* condition */ msg.sender == oracle, "Not oracle");

If the condition is true, execution continues. If false, the entire transaction reverts and the user sees the error message.

Globals every function gets for free

5. Control flow and the linear-procedural shape

Solidity has if / else, for, while, do-while, break, continue, recursion — the full procedural toolkit. But idiomatic contracts use very little of it. Functions tend to be short, linear, and procedural. Three pressures push them this way:

Gas economics. Every operation costs gas, and a transaction can spend at most about 30 million gas on Ethereum mainnet. A loop iterating over an array whose length can grow without bound — for example, every user the contract has ever seen — will eventually run out of gas and revert. So unbounded loops are an anti-pattern. Bounded loops over short fixed-size lists are fine.

Atomicity. Because state changes roll back atomically on a revert, there is no benefit to elaborate try-it-and-recover code paths. Either the whole call succeeds or none of it happened. This kills the motivation for complicated branching.

Reentrancy. If your function makes an external call to another contract before all of your own state changes are written, the called contract can re-enter your function and observe inconsistent state — the famous DAO attack from 2016. The defence is the checks-effects-interactions pattern:

  1. Checks. All your require validations at the top of the function.
  2. Effects. All your state changes next.
  3. Interactions. External calls (token transfers, oracle queries, etc.) last.

The result is that idiomatic Solidity functions look like a downhill slope: validate, mutate, emit, call out. SolidiFlow's IR mirrors this shape on purpose — the visual primitives don't include a "loop" node, and Function Nodes flow naturally as validate → state change → event → external call.

7. Each visual primitive, and what it generates

This section walks through the nine node types in the SolidiFlow IR (see the IR schema doc for the JSON shapes) and shows what each one produces in Solidity.

State Node → state variable

A State Node represents a single piece of persistent contract data. Its property panel exposes: name, type, visibility, constant / immutable / neither, and an optional initial value. The generator emits one Solidity state variable declaration per State Node. Already covered in detail in section 6.

Function Node → function

A Function Node represents a callable function. The user fills in: name, visibility, mutability, parameters, returns, and a list of modifiers attached to it.

function mint(address contributor, uint256 amount)
    external
    onlyOracle
{
    _mint(contributor, amount);
    emit Mint(contributor, amount);
}

Visibility options:

KeywordWho can call itWhen to use
externalOnly callers from outside the contract.User-facing functions. Cheaper than public for large argument lists.
publicExternal callers and other functions inside this contract.When you need both. Slightly less efficient than external.
internalThis contract and contracts that inherit it.Shared helpers. ERC-20's _mint / _burn / _transfer are internal.
privateThis exact contract only.Rare in practice. internal is more common.

Mutability options:

KeywordPromiseEffect
viewWon't modify state.Free to call from off-chain readers; gas-free.
pureWon't even read state.Pure computation. Fully off-chain-callable.
payableWilling to accept ETH.Without this, sending ETH to the function reverts.
(unspecified)Default nonpayable.Can read and write state; rejects ETH.

Modifier Node → modifier

A Modifier Node represents a reusable pre-condition that wraps any function it's attached to.

modifier onlyOracle() {
    require(msg.sender == oracle, "Not oracle");
    _;
}

The _; is the magic. It marks the spot where the wrapped function's body gets inserted at compile time. So function mint(...) external onlyOracle { ... } compiles to roughly:

function mint(...) external {
    require(msg.sender == oracle, "Not oracle");
    // <original body of mint>
}

If the require fails, the function never runs. Multiple modifiers stack in declaration order. SolidiFlow models the attachment as a property of the Function Node (a list of modifier IDs) rather than as a graph edge, because the attachment is part of the function's signature.

Condition Node → require / if-else

Condition Nodes have two flavours, captured by their style property. style: "require" compiles to:

require(msg.sender == oracle, "Not oracle");

If the expression is true, execution continues. If false, the transaction reverts with the message. style: "ifElse" compiles to a normal branch:

if (block.timestamp >= deadline) {
    // pass branch
} else {
    // fail branch
}

The pass and fail source handles on the Condition Node map directly to which branch the downstream nodes belong to. For require style, only pass continues; fail triggers the revert and is left unwired.

Event Node → event + emit

Events write entries to the chain log — a special append-only stream visible to off-chain readers (block explorers, dapp frontends, indexers) but not readable from inside Solidity. They exist mostly so user interfaces can detect that something happened without polling the contract's state. The declaration:

event Mint(address indexed to, uint256 amount);

indexed makes that parameter searchable in the log; you can filter "every Mint to address X." Up to three indexed params per event. The emit:

emit Mint(contributor, amount);

The Event Node is the declaration; the emit is a sideEffect edge from a Function Node to the Event Node. The same Event Node can be emitted from many functions; each function-to-event link is its own edge.

Time Trigger Node → block.timestamp comparison

A Time Trigger Node is a specialised Condition Node — semantically the same shape but flagged for the editor (clock icon) and the generator (recognise time-decay patterns). It compiles to:

require(block.timestamp >= deadline, "Too early");

The whole "consensus determinism forbids real-world time" caveat applies: block.timestamp is the block timestamp, deterministic across nodes (because they read it from the same block header) but coarse and validator-influenceable. Fine for "after deadline" logic; useless for finer-grained timing.

External Call Node → interface call

Calling a different deployed contract goes through that contract's interface:

interface IERC20 {
    function transferFrom(address from, address to, uint256 amount)
        external
        returns (bool);
}

contract Example {
    IERC20 public usdc;

    function deposit(uint256 amount) external {
        bool ok = usdc.transferFrom(msg.sender, address(this), amount);
        require(ok, "USDC transfer failed");
    }
}

IERC20(usdcAddress).transferFrom(...) reads "treat the contract at usdcAddress as if it implements IERC20's function signatures, and call transferFrom." If the target doesn't actually implement that signature, you get a runtime revert.

Phase Node → enum + state variable + guards

Phase Nodes compile to three coordinated pieces of Solidity: an enum declaring the phase names, a state variable holding the current phase, and (optionally auto-injected) require guards in each phase-scoped function.

enum Phase { PoD, PoM, PoR }
Phase public currentPhase;

function submitDeliverable() external {
    require(currentPhase == Phase.PoD, "Not in PoD");
    // ...
}

function advanceToPoM() external {
    require(currentPhase == Phase.PoD, "Not in PoD");
    require(block.timestamp >= deliveryDeadline, "PoD not over");
    currentPhase = Phase.PoM;
}

enum is a named integer; Phase.PoD is 0, Phase.PoM is 1, Phase.PoR is 2. The enumIndex property on a Phase Node controls this ordering.

Each phaseTransition edge between two Phase Nodes becomes an advance function that checks the source phase, evaluates the guard condition, and writes the new phase. SolidiFlow generates these advance functions automatically.

Token Flow Arrow → transfer / transferFrom / internal _transfer

The only IR primitive that has multiple Solidity translations depending on context. Three cases:

Native ETH transfer (when tokenStandard is "native"):

(bool ok,) = recipient.call{value: amount}("");
require(ok, "ETH transfer failed");

External ERC-20 transfer (when the token is a different contract from the one being authored):

bool ok = IERC20(tokenAddress).transferFrom(from, to, amount);
require(ok, "Transfer failed");

Self-token transfer (when the contract being authored is the ERC-20):

_transfer(from, to, amount);   // moves tokens between two holders
_mint(to, amount);              // creates new tokens
_burn(from, amount);            // destroys tokens

These _-prefixed functions come from OpenZeppelin's ERC20.sol when you do contract CompuToken is ERC20. They're cheaper, don't trigger reentrancy concerns, and are idiomatic.

Open question

Whether SolidiFlow auto-detects "this Token Flow operates on the contract's own ERC-20 balance" and emits the internal _transfer form, or requires the user to mark it explicitly, is one of the three deferred IR design decisions. Discussed in section 10.

8. Worked example: CompuToken end-to-end

Audience for this section

Audience 1 (SolidiFlow user, specifically a contract author for P2PCP) checking the generator output. Audience 4 (Solidity reader) sanity-checking the contract.

Putting all the pieces together, here is what SolidiFlow's generator should emit when given the CompuToken IR from the IR schema doc:

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";

/// @title CompuToken — the P2PCP token
/// @notice Minted when verified compute is contributed; burned when consumed.
contract CompuToken is ERC20 {
    address public immutable oracle;

    event Mint(address indexed to, uint256 amount);
    event Burn(address indexed from, uint256 amount);

    modifier onlyOracle() {
        require(msg.sender == oracle, "Not oracle");
        _;
    }

    constructor(address _oracle) ERC20("CompuToken", "CMPT") {
        oracle = _oracle;
    }

    function mint(address contributor, uint256 computeUnits)
        external
        onlyOracle
    {
        _mint(contributor, computeUnits);
        emit Mint(contributor, computeUnits);
    }

    function burn(address consumer, uint256 computeUnits)
        external
        onlyOracle
    {
        _burn(consumer, computeUnits);
        emit Burn(consumer, computeUnits);
    }
}

What came from where:

Saving and re-loading the IR should produce byte-identical Solidity. That's the round-trip property the IR is designed to preserve.

9. Worked example: CGP three-phase agent (partial)

The CGP partial example becomes:

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract CGPAgent {
    enum Phase { PoD, PoM, PoR }
    Phase public currentPhase;

    uint256 public deliveryDeadline;
    uint256 public measureDeadline;

    function advanceToPoM() external {
        require(currentPhase == Phase.PoD, "Not in PoD");
        require(block.timestamp >= deliveryDeadline, "PoD not over");
        currentPhase = Phase.PoM;
    }

    function advanceToPoR() external {
        require(currentPhase == Phase.PoM, "Not in PoM");
        require(block.timestamp >= measureDeadline, "PoM not over");
        currentPhase = Phase.PoR;
    }

    // submitDeliverable, postMeasurement, resolve to be added —
    // each begins with require(currentPhase == Phase.<correct>, "...")
}

The advance functions are generated entirely from the phaseTransition edges in figure 3. The phase guards on the user-facing functions (submitDeliverable, postMeasurement, resolve) are what would be auto-injected if SolidiFlow takes the auto-inject interpretation of open question 2 below.

10. Three deferred IR design questions, restated

The IR draft surfaced nine open questions. Three of them shape what code the generator emits, and have a tangible answer once the rest of this primer has been read.

Question A. Self-token Token Flow auto-detection

Setup. When the user draws a Token Flow arrow on a contract that is an ERC-20 (such as CompuToken), the arrow could mean either of two things:

  • "Move tokens using this contract's own internal balance bookkeeping" → emit _mint / _burn / _transfer.
  • "Treat this contract like any other ERC-20 and call its public functions" → emit a regular external transferFrom.

Stakes. Internal calls are cheaper, idiomatic, and don't raise reentrancy concerns. External calls are how you'd interact with a different ERC-20 (USDC, DAI, etc.) from inside CompuToken's code.

Recommendation. Auto-detect by default (visual arrow targeting the same contract that contains it → internal form). Surface the choice in the property panel as an "internal / external" toggle so users can override when needed.

Question B. Phase-scoped Function auto-guard

Setup. When a Function Node is in a Phase Node's attachedFunctionIds, the user is saying "this function belongs to this phase." For the Solidity to actually enforce the phase — so e.g. submitDeliverable can't be called during PoR — there needs to be a require(currentPhase == Phase.PoD) at the top of the function body.

Stakes. Auto-injecting that require matches user intuition (drawing a function inside a phase means it's only callable in that phase). Requiring an explicit Condition Node is more verbose, but more visible.

Recommendation. Auto-inject by default, with an opt-out flag in the Function Node's data for cases where the user wants the function callable across phases.

Question C. Constructor as a Function Node or its own type

Setup. Constructors in Solidity are special. They run once at deployment, can take parameters that influence the deployed contract's permanent configuration, can set immutable state variables (which regular functions can't), and don't have external / public visibility (they're called by the deployment process, not afterwards).

Stakes. Modelling a constructor as a regular Function Node with name == "constructor" works syntactically but conflates it with normal methods in the visual layer. A dedicated Constructor Node type is more honest and lets the editor surface the special bits (initial values for immutables, inherited constructor calls like ERC20's name/symbol).

Recommendation. Dedicated Constructor Node type in v0.1. Both CGP and P2PCP need constructors immediately (oracle address, ERC-20 name/symbol, initial deadlines), so this will show up.

11. Exercises

Quick reinforcement. Skim the answers in your head; verify against the rest of the primer if you're not sure.

Exercise 1 — tag the tokens

For the line below, identify each token's category: mandated, chosen, or syntax punctuation.

uint256 internal totalContributed = 0;

Answer: uint256 mandated (type), internal mandated (visibility), totalContributed chosen (name), = punctuation, 0 chosen (initial value, freely picked), ; punctuation.

Exercise 2 — predict the output

A SolidiFlow user drags a Function Node onto the canvas, names it distribute, sets visibility external, mutability nonpayable, parameter amount of type uint256. They attach an onlyOwner modifier. They wire one sideEffect edge to an Event Node named Distributed with parameters (address indexed to, uint256 amount).

What does the function declaration line look like in Solidity (without the body)?

Answer:

function distribute(uint256 amount) external onlyOwner

Exercise 3 — spot the determinism violation

A user wants to write a function that picks a random winner from a list of contributors. They imagine: "the contract calls random() and uses that to pick an index." Why doesn't this work, and what would they need to use instead?

Answer: Solidity has no random(), because every Ethereum node would compute a different value and consensus would break. The contract would need to either (a) derive a deterministic pseudo-random index from on-chain data like block.prevrandao (every node sees the same value, but it's predictable and weak), or (b) use a verifiable random oracle service like Chainlink VRF.

Exercise 4 — decide the IR question

You're authoring the CompuToken contract in SolidiFlow. You draw a Token Flow arrow representing "burn 100 CMPT from the consumer." The contract is itself the CMPT ERC-20.

Under the recommended interpretation of question A, what Solidity does the generator emit?

Answer: _burn(consumer, 100); — auto-detected as a self-token operation, so the internal form is used.

Exercise 5 — trace an exception

A user calls mint(0xAAA..., 50) on CompuToken, but they are not the oracle. Walk through what happens.

Answer: The transaction reaches CompuToken's mint function. The onlyOracle modifier runs first, executing require(msg.sender == oracle, "Not oracle"). Because the caller is not the oracle, the require fails. Execution stops; no _mint happens; no event is emitted; all state changes (none yet, but if any had been made) roll back atomically. The user pays gas for the work done up to the revert. They see the error message "Not oracle".

In rough order of usefulness for SolidiFlow's design space:

13. What this primer doesn't cover

Things that exist in real Solidity contracts but that SolidiFlow's v0 deliberately does not try to express:

  • Inline assembly (assembly { ... }) — bypasses Solidity's safety net, not in scope.
  • Custom errors (error InsufficientBalance(...)) — gas-efficient, will appear in v0.1 once the Condition Node grows a richer error mode.
  • Libraries (library SafeMath) — the patterns SolidiFlow needs are mostly covered by Solidity 0.8's built-in overflow checks plus OpenZeppelin's contracts.
  • Upgrade patterns (proxies, UUPS, transparent) — explicitly out of scope per the seed document. immutable is fine for the protocols SolidiFlow serves.
  • Yul, low-level call / delegatecall semantics, fallback / receive functions — not needed for the visual layer's target contracts.
  • Mining, proof-of-work / proof-of-stake details, validator selection — covered briefly in the consensus discussion, not relevant to authoring contracts.

When SolidiFlow eventually outgrows what's covered here, this primer grows with it.
